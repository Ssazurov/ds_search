# ADR-001: MVP-архитектура сбора данных и интеграция с существующей GAR RAG-платформой

Статус: Proposed
Дата: 2026-08-23

## Контекст

Видение проекта (`видение_проекта.md`) описывает 5 блоков: Extract → Transform →
Load → Analytics → RAG. Предполагалось, что RAG "уже существует", но её стек не
был описан. Выяснено: RAG — это GAR-платформа (`~/projects/gar-core-api` +
`gar-docling-intake` + `gar-admin-ui`), стек: FastAPI, SQLAlchemy2/Postgres,
Qdrant, BM25(rank-bm25+pymorphy3), Docling-интейк, ограничение форматов на входе
`.pdf/.md/.docx/.txt`. У GAR уже есть собственная схема метаданных (`metadata_schema.yaml`
в gar-docling-intake), заточенная под техдокументацию (product/doc_type/version) —
не подходит напрямую под домен "синдром Дауна" (нужны source_url, license,
author, age_group и т.д.).

## Решения

1. **Не дублировать RAG.** ds_ingestion не строит свой индексатор/чанкер/вектор-
   стор — использует существующий пайплайн gar-core-api + gar-docling-intake.
   ds_ingestion = адаптер: конвертация в допустимые форматы (.pdf/.md/.docx/.txt) →
   вызов ingestion API GAR.
2. **Доменный профиль метаданных** для этого проекта заводится отдельно от
   продуктовой схемы gar-docling-intake (не трогаем существующие
   product/doc_type/version поля без разрешения — правило AGENTS.md GAR).
   Финальная схема (уточнена 2026-08-23 по результатам анализа классификации
   источников):
   - `source_url`, `source_domain`, `title` — идентификация документа;
   - `license` / `redistribution_status` — результат проверки лицензии/ToS
     источника (см. п.3), обязательное поле наравне с source_url;
   - `direction` (enum: methodology / medicine / law / science) — верхнеуровневое
     направление, соответствует разделам 3.1–3.3 видения;
   - `category` — категория внутри направления (напр. speech_development,
     social_protection). **Контролируемый словарь**, не свободный текст —
     ведётся в `config/categories.yaml` (уже заложен в структуре проекта),
     чтобы избежать неограниченного роста уникальных значений;
   - `doc_type` (enum: book/guide/article/law/dissertation/clinical_recommendation/
     brochure/program и т.п.) — формат документа, отдельно от `direction`;
   - `target_audience` (enum: parents/specialists/researchers) — не выводится
     автоматически из direction, т.к. один документ может читаться разными
     аудиториями (напр. право читают и родители, и соцработники);
   - `author`, `publish_date`, `description`, `keywords`, `age_group` — как в
     видении.
   **Исключено из doc_type**: "медицинские карты" — реальные персональные
   медицинские записи пациентов собирать нельзя (риск нарушения 152-ФЗ и
   врачебной тайны); в медицинском направлении собираются только
   обезличенные материалы (статьи, клинические рекомендации, обзоры).
   **Механизм записи решён (2026-08-25, issue #4):** используется
   существующий в gar-core-api per-dataset динамический словарь метаданных
   (`DatasetMetadataField`/`DatasetMetadataOption`, Postgres-таблицы уже
   есть, роутер `routers/metadata_dictionary.py`,
   `POST /datasets/{id}/metadata-fields`) — НЕ расширение
   `metadata_schema.yaml` gar-docling-intake (та схема специфична под
   product/doc_type техдокументации, часть её полей `required=True` завязаны
   на product/product_version) и НЕ отдельная новая Postgres-таблица
   (дублировала бы уже существующий механизм). Адаптер (issue #5) заводит
   поля профиля через этот API на датасете GAR для синдрома Дауна один раз
   при инициализации: `value_type="text"` для строковых полей
   (source_url/title/author/...), `value_type="select"` с опциями из
   `config/categories.yaml`/enum'ов для direction/category/doc_type/
   target_audience/license. Константы и загрузчик `config/categories.yaml`
   зафиксированы в `src/metadata/schema.py`.
3. **Проверка лицензии/ToS обязательна до скачивания.** Перед сбором с каждого
   источника — анализ лицензии/условий использования сайта:
   - если требуется атрибуция — она формируется и пишется в метаданные
     (author/source attribution) и сохраняется вместе с документом;
   - если автосбор/скачивание запрещено явно — документ не скачивается,
     источник помечается "требует ручного сбора", пользователь уведомляется;
   - результат проверки (allow/attribution-required/deny) — обязательное поле
     `license` при загрузке в RAG.
3a. **Очистка и фильтрация контента — обязательный этап между краулингом и
    загрузкой в GAR** (уточнено 2026-08-24 по результатам ручного анализа
    первого прогона на downsideup.org). Crawl4AI отдаёт markdown "как есть" —
    в нём остаётся навигация сайта, футер, версия для слабовидящих и т.п.,
    а часть страниц по сути являются "пустышками" (видео с короткой подписью,
    без содержательного текста). Решение:
    - шаг очистки (strip nav/header/footer/меню/спецверсий) выполняется до
      Docling-конвертации, отдельным модулем в ds_search (не в GAR);
    - после очистки считается объём полезного текста; документы ниже порога
      (или помеченные как "видео без текстового материала") помечаются
      `content_status: rejected_thin_content` и не идут в загрузку — вместо
      блокирующей ошибки фиксируются в отчёте для точечной ручной проверки;
    - критерии/пороги фиксируются в отдельном issue при реализации, чтобы не
      блокировать MVP выбором точного числа сейчас.
    - **Уточнено 2026-08-25 (research: boilerplate removal для RAG).**
      Не писать свой regex-парсер под strip nav/footer — использовать
      готовый density-based content filter, встроенный в уже используемый
      Crawl4AI (`DefaultMarkdownGenerator(content_filter=PruningContentFilter(...))`,
      даёт `result.markdown.fit_markdown`), а не подключать отдельно
      Trafilatura/Boilerpipe. Метрика отсева — link-to-text ratio (LTR):
      страницы с высокой долей ссылок в тексте (>20-30%) — листинги/навигация,
      статьи — обычно <15%. Модуль очистки issue #6 = включить фильтр в
      `CrawlerRunConfig` + порог по LTR/объёму `fit_markdown`, а не отдельный
      парсер с нуля.
    - **Подтверждено замером 2026-08-25** (ручная проверка 8 файлов
      downsideup.org): статьи LTR 0.05-0.12, каталоги/листинги LTR 0.48-0.86 —
      граница чёткая, порог **LTR > 0.2-0.3** отсекает все каталожные
      страницы без потери статей. LTR не ловит тематическую нерелевантность
      (пример: статья "Как мы привлекаем средства" — фандрайзинг фонда,
      LTR=0.12, но не по теме синдрома Дауна) — нужен отдельный фильтр по
      ключевым словам/разделу URL, LTR его не заменяет.
3b. **Отбор страниц при краулинге уточнён** по результатам ручного разбора
    корпуса downsideup.org — 100 собранных документов (2026-08-25, см. также
    issue по улучшению фильтров краулера). Найдено: заметная доля страниц —
    не статьи, а служебные/листинговые (повторяющийся шаблонный title вида
    "Электронная библиотека -..." — JS-виджет карточек не успевает
    отрендериться, текст статьи недоступен; страницы-листинги
    "Аналитика для прогресса"/"Новости" с пагинацией `?PAGEN_1=N`; главная
    страница-дубль; интерактивные инструменты — дневник развития, форум,
    календарь, регистрация). Причина: `EXCLUDE_PATTERNS` в
    `src/crawler/filters.py` написаны как англоязычные слаги (`*/news/*`,
    `*/events/*`), а реальные URL источника — транслит русских разделов
    (`o-fonde/novosti/`, `roditelyam/kalendar-sobytiy/`), фильтр не
    срабатывает ни разу. Решение:
    - exclude-паттерны переносятся в `SourceConfig` как список конкретных
      слагов источника (не общий хардкод под англоязычные CMS);
    - добавляется фильтр URL с параметрами пагинации (`?PAGEN_1=` и т.п.);
    - страницы-тизеры к PDF-отчётам (карточка с описанием и ссылкой
      "скачать/открыть отчёт") не отбрасываются и не сохраняются как
      html-документ — вместо этого сам PDF скачивается прямым http-запросом
      (не `browser.goto`, известная проблема issue #2 — Playwright трактует
      переход на файл как "Download is starting"). **Уточнено 2026-08-25
      (issue #11):** детект тизера не может опираться на порог длины
      fit_markdown — у карточки часто есть блок "Похожие материалы" (список
      ссылок), который легко проходит `min_fit_markdown_chars` при
      отсутствии реального текста статьи; признак тизера — маркер "скачать/
      открыть отчёт" рядом с `.pdf`-ссылкой в html, проверяется до фильтра
      по длине;
    - `KeywordRelevanceScorer` сейчас только ранжирует очередь обхода, не
      отсекает документы — добавляется hard-cutoff порог релевантности
      перед сохранением в `data/raw`, чтобы не плодить заведомый мусор
      ещё до этапа очистки (п.3a).

4. **Правовые источники.** КонсультантПлюс/ГАРАНТ исключены из автосбора
   (ToS запрещает). Заменяются открытыми гос. источниками (напр.
   publication.pravo.gov.ru, региональные минздравы) там, где это покрывает
   нужный контент.
5. **Postgres — с фазы 1.** Уже развёрнут (используется GAR), доменные таблицы
   документов заводятся сразу, миграция с JSON не нужна.
6. **Docling уже есть** (`gar-docling-intake`) — используется как основной
   PDF/DOCX→структура парсер вместо отдельного PyMuPDF4LLM-пайплайна.
   **Пропускная способность (issue #5, 2026-08-25):** сервис — один
   GPU-контейнер без пула воркеров (`main.py`: на каждый запрос — отдельный
   subprocess, таймаут 600с на таблицы/большие PDF). Параллельные запросы
   от адаптера будут конкурировать за GPU без выигрыша в throughput, поэтому
   `ds_ingestion` грузит документы источника **последовательно**, не пулом.
   Живой замер докс/час не проводился (не входит в MVP) — перед полным
   прогоном на ~1000+ документах рекомендуется ручной смоук-тест на 5-10
   файлах для оценки времени.
7. **Краулер** — Crawl4AI (self-hosted, Apache-2.0), т.к. данные чувствительные
   (медицина/дети/право), managed-сервисы (Firecrawl/Apify) исключены.
8. **Сопровождение** — уточняется пользователем (соло/команда), не блокирует
   MVP-решения выше; влияет только на выбор оркестрации (cron-скрипт на старте,
   Prefect/Airflow — если появится команда, отдельным ADR).

## Последствия

- ds_search и ds_ingestion становятся сателлитами GAR, а не независимым
  RAG-стеком — меньше кода, риск рассинхронизации схем компенсируется
  согласованием доменного профиля метаданных с gar-core-api.
- Появляется новый обязательный этап пайплайна — лицензионная проверка
  источника — раньше в видении отсутствовал.
- Видение (`видение_проекта.md`) требует правки: раздел 2.1 (Postgres как
  "новая" БД) и раздел 6.1 (requirements.txt с pymupdf) — уточнить как
  "используется существующая инфраструктура GAR" отдельным изменением после
  подтверждения ADR.
