# ADR-002: Discovery+курация вместо полного автокраулинга, UI для поиска и справочников

Статус: Accepted
Дата: 2026-08-26

## Контекст

ADR-001 задал MVP на базе автокраулинга (Crawl4AI + фильтры LTR/keyword,
п.3a/3b). Даже после доработки фильтров (issue про exclude-паттерны,
детект тизеров) полный автообход даёт заметную долю мусора и не даёт
контроля над тем, что именно попадает в базу — риск признан пользователем
неоправданным для основного режима работы.

Предложена смена модели: система **ищет** источники (не обходит сайты
целиком), показывает находки в UI с метаданными и оценкой релевантности,
пользователь **курирует** (одобряет/отклоняет/правит категории) и решает,
что скачивать — вручную или пакетно.

## Решения

1. **Поиск — через готовый Search API, не свой скрапинг выдачи.**
   Скрапинг SERP (Google/Yandex/Bing через headless-браузер) прямо запрещён
   ToS поисковиков — риск бана IP/CAPTCHA и отдельная юридическая экспозиция
   помимо ToS сайтов-источников (ADR-001 п.3). Используем официальный
   платный/freemium API (Google Programmable Search JSON API, Bing/Brave
   Search API, либо обёртки типа Serper/SerpAPI). Выбор провайдера —
   открытый вопрос (см. ниже), не блокирует остальные решения ADR.

2. **Релевантность на этапе поиска считается по сниппету, не по полному
   тексту страницы.** API поиска отдаёт только заголовок+короткий
   сниппет — страница ещё не скачана. Скоринг (BM25/keyword-overlap по
   сниппету, возможно + LLM-классификация сниппета) — черновая
   предфильтрация для сортировки в UI, не финальное решение о релевантности.
   Полноценная проверка (LTR/keyword-фильтр по `fit_markdown`, ADR-001
   п.3a/3b) остаётся на этапе после скачивания и уточняет/переопределяет
   предварительную оценку.

3. **Новая таблица `discovered_sources`** (кандидаты из поиска).
   Поля: `id`, `url` (норм.), `domain`, `title`, `snippet`, `found_at`,
   `search_run_id` (FK — какой поиск/тема нашёл), `relevance_score`,
   `suggested_direction/category/doc_type/target_audience` (nullable,
   editable пользователем), `license_status` (по умолчанию `unknown` —
   проверка лицензии/ToS (issue #3) запускается лениво только при `approve`,
   не на все находки сразу), `is_duplicate` (bool, по норм. URL против уже
   загруженных документов и прошлых находок), `status`
   (`new/approved/rejected/queued/downloading/downloaded/error`).

4. **UI — отдельное приложение**, архитектурно по образцу `gar-admin-ui`
   (Next.js App Router, react-aria, `app/<раздел>/page.tsx` +
   `app/api/<раздел>/route.ts`, справочники по образцу
   `MetadataDictionarySettings.tsx`). Не встраивается в `gar-admin-ui`
   (другой репозиторий/домен) — отдельный сервис в `ds_search` или новый
   репозиторий (см. открытые вопросы).

   Блоки UI:
   - **Справочники** — CRUD (direction/category/doc_type/target_audience/
     age_group/license_status), обязательное значение по умолчанию
     "не выбрано" во всех select'ах (не пустая строка/0 — чтобы не путать
     с валидным значением словаря).
   - **Очередь предложенных значений словарей** (`dictionary_suggestions`) —
     новые значения от авто-классификатора при разборе находок, статус
     pending/approved/rejected, не пишутся в основной словарь напрямую.
   - **Результаты поиска** — таблица `discovered_sources`: колонки url/title/
     snippet/domain/direction/category/doc_type/relevance_score/
     license_status/is_duplicate/status/found_at; фильтры по каждому полю +
     полнотекстовый; пагинация; чекбоксы + bulk-действия (одобрить/
     отклонить/поставить в очередь загрузки); дубли визуально помечены и
     по умолчанию скрыты за фильтром.
   - **Загрузка** — очередь одобренных + вручную вставленных URL, статус на
     элемент (queued/downloading/done/error), retry, ссылка на итоговый
     локальный путь/документ после обработки.
   - **Параметры поиска** — тема (текст), direction/category/target_audience
     (select, default "не выбрано"), период, кнопка "запустить поиск",
     сохранённые пресеты для периодических/плановых поисков.
   - **Документы** — уже загруженные, статус по стадиям пайплайна
     (raw → clean → metadata → GAR ingested), ссылка на датасет GAR.
   - **Источники/домены** — реестр доменов с известным ToS-статусом
     (переиспользует license checker issue #3), whitelist/blacklist.
   - **Дашборд** — воронка found → approved → downloaded → ingested,
     разбивка по категориям/направлениям, ошибки последних запусков.

5. **Ручная загрузка — не "просто файл в папку".** Без исходной веб-страницы
   нет источника для автоизвлечения метаданных, а `license`/`source_url` —
   обязательные поля (ADR-001 п.2-3). Минимальный flow: форма в блоке
   "Загрузка" — путь к локальному файлу или drag-drop, обязательные поля
   метаданных заполняются пользователем вручную; дальше документ идёт по
   тому же пайплайну (шаг 3a "очистка" неприменим/пропускается для не-HTML
   источника; 4 "метаданные" — введены руками, а не извлечены; 5 GAR
   ingestion — как обычно). Отдельного кода "мониторинга папки" не нужно —
   один explicit entry point (UI-форма или CLI-аналог) вместо неявного
   сканирования директории.

6. **Дедупликация на этапе находок** — по нормализованному URL против (а)
   уже загруженных документов, (б) прошлых находок (approved/rejected/
   downloaded) из предыдущих запусков поиска — не только внутри текущего
   прогона.

## Последствия

- Автокраулинг (Crawl4AI + фильтры ADR-001 п.3a/3b) не отменяется, но
  перестаёт быть основным путём сбора — становится опциональным батч-
  режимом поверх уже одобренных доменов/разделов, если понадобится.
- Появляется новый компонент сопровождения — UI-приложение (деплой,
  доступ). На MVP предполагается локальный доступ без авторизации
  (соло-разработка) — явно зафиксировать при реализации.
- Новая внешняя зависимость — платный/квотируемый Search API — бюджетный
  вопрос, не только технический.
- Схема БД растёт минимум на 2 таблицы (`discovered_sources`,
  `dictionary_suggestions`); возможен перенос словарей из
  `config/categories.yaml` в БД (см. открытые вопросы) — это отдельное
  архитектурное решение, YAML пока остаётся источником правды для адаптера
  issue #5, пока не решено иначе.

## Уточнения 2026-08-26

**Bing Search API исключён.** Официально закрыт Microsoft 11.08.2025, новые
ключи не выдаются — не рассматривается как вариант.

**Как ищут агенты и почему их не банят.** Агенты (включая web_search у
Claude) не скрапят HTML-выдачу гугла напрямую — они ходят через
лицензированный backend-провайдер поиска (коммерческий API-доступ). Это и
есть единственный устойчивый к бану путь: скрапинг SERP всегда рискует
IP-баном/капчей независимо от того, кто его делает — агент или скрипт.
"Агенты не банят" — иллюзия: у них просто платный контракт с провайдером,
а не magic bypass.

**Решение — провайдер Search API с fallback-цепочкой, не единственный
провайдер.** Заводится абстракция `search_provider` (интерфейс: query →
список {url, title, snippet}) с несколькими реализациями и раунд-робин/
fallback по исчерпанию дневной квоты (счётчик расходов на провайдера в БД
или простой файл-стейт). Стартовый набор бесплатных/дешёвых уровней
(уточнить актуальные условия перед реализацией — меняются часто):
- Google Programmable Search JSON API — 100 запросов/день free;
- Brave Search API — независимый индекс, free-tier порядка 1000-2000
  запросов/месяц;
- Tavily / Exa — API "для AI-агентов", отдают уже готовый
  сниппет+релевантность под RAG-сценарии, free-tier порядка 1000
  запросов(кредитов)/месяц — по формату ответа может подойти лучше "сырых"
  SERP-API, т.к. заточены именно под этот use case (кандидат на основной
  провайдер, не только fallback).
Точные лимиты/цены проверяются перед реализацией (issue), т.к. официальные
условия у всех провайдеров периодически меняются.

**Решение — этап "probe" (частичная загрузка) между поиском и полным
скачиванием.** Добавляется промежуточный шаг: по URL из
`discovered_sources` делается HTTP GET с ограничением объёма (cap ~2 МБ,
через потоковое чтение с обрывом по достижении лимита — не полноценный
рендеринг браузером). Полученный (возможно, обрезанный) HTML прогоняется
через уже используемый в проекте Crawl4AI content-filter
(`PruningContentFilter`/`fit_markdown`, ADR-001 п.3a) для расчёта LTR и
объёма полезного текста — то есть тот же критерий, что уже отсекает
навигацию/листинги при краулинге, применяется здесь раньше, до решения о
полном скачивании. Уточняет предварительный `relevance_score` по сниппету
(решение 2 выше) более сильным сигналом на основе реального контента,
не только заголовка.
- Ограничение: probe без JS-рендеринга (обычный httpx, не Playwright) —
  для SPA-страниц, где контент подгружается скриптом, probe может дать
  пустой/бедный результат. В этом случае `relevance_score` остаётся на
  уровне сниппета, документ не отсеивается автоматически, а помечается на
  ручной просмотр (не блокирующая ошибка, как и thin-content в ADR-001 п.3a).
- Полное скачивание (с браузером, если нужно) происходит только после
  `approve` пользователем — probe не заменяет его, а помогает
  предфильтровать/отсортировать до этого момента.

**Решение — ручная загрузка (подтверждено пользователем).** Два пути в
блоке "Загрузка":
  a) Файл + метаданные вручную → система сохраняет файл в `data/raw/` (или
     сразу в `data/clean/`, т.к. очистка для не-HTML неприменима) + создаёт
     JSON-метафайл с введёнными полями, дальше — этап 4 (обогащение, если
     применимо) → этап 5 (GAR ingestion), как обычно.
  b) Ссылка на сайт → стандартный пайп с этапа "лицензия/ToS" (ADR-001
     п.3), т.е. ровно как одобренная находка из `discovered_sources`.

## Решено 2026-08-26 (финал)

2. **Словари — источник правды остаётся `config/categories.yaml`.** UI
   (Streamlit, см. п.3) читает/пишет напрямую в YAML, без БД-дублирования
   справочников. Адаптер issue #5 продолжает читать тот же файл — изменений
   в issue #4/#5 логике не требуется.
3. **UI — Streamlit, подкаталог `ds_search/ui/` (не отдельный репозиторий,
   не Next.js).** Отменяет решение 4 из основного текста ADR (там был
   черновой вариант "по образцу gar-admin-ui") — Next.js-вариант отклонён
   как избыточный для соло-разработки и MVP-скорости. `discovered_sources`
   и `dictionary_suggestions` (БД) читаются/пишутся напрямую из Streamlit;
   `gar-admin-ui` как референс для UX-паттернов (таблицы/фильтры/статусы)
   остаётся полезным, но не как код-база для копирования.
4. **Авторизация UI — не нужна на MVP.** Локальный доступ (соло-режим),
   без auth-слоя.
6. **LLM-классификатор поверх сниппета/probe-контента для
   direction/category — нужен, но низкий приоритет.** На MVP: keyword/
   BM25-эвристика по словарям из `categories.yaml` (дёшево, без внешних
   вызовов). LLM-классификация — отдельная задача после MVP, не блокирует
   первый релиз discovery-модуля.

## Уточнения 2026-08-26 (проверка перед реализацией issue #15)

Актуальные условия провайдеров (проверено веб-поиском):
- **Google Programmable Search JSON API** — закрыт для новых регистраций,
  доступен только существующим клиентам; полное отключение 1 января 2027.
  Исключён из выбора для нового проекта.
- **Brave Search API** — бесплатный tier без карты убран в феврале 2026.
  Теперь только $5/мес кредитов при привязанной карте (~1000 запросов),
  дальше платно без верхнего лимита списаний. Отложен: не подключаем без
  отдельного решения о карте/бюджете.
- **Tavily** — единственный из рассмотренных с реальным free-tier без
  карты (1000 кредитов/мес). Выбран единственным активным провайдером на
  старте; `search_provider` реализуется как абстракция с fallback-цепочкой
  (для будущих провайдеров), но цепочка сейчас состоит из одного элемента.

## Открытые вопросы
